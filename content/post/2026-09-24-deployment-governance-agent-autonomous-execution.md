最近终于把部署服务做通了。回头看，真正拖慢开发的并不是某一个命令，而是运行环境没有为 Agent 的持续执行做好准备。

## 先解决环境，再要求 Agent 自主执行

过去每次修改后重新启动服务，都要反复输入管理员密码。多账号隔离本来是为了安全，却让部署过程被拆成一连串人工确认：查问题、绕过限制、再次输入密码，最后才能上线。

后来我把部署本身做成一个严格的服务：由管理员权限启动，但只负责部署这一件事。完成这个基础服务后，Agent 不再需要每一步都停下来等我输入密码，而是可以在配置好的环境里继续执行目标。

这让我更清楚地意识到，所谓“让 Agent 自主”，不是简单地对它说“自己完成”，而是提前把权限、工具、校验和流程配置好。环境不合适时，Agent 只能不断请求人工帮助；环境合适时，它才有可能持续工作到完成。

## 治理要先于放权

我的一个重要经验是：治理要尽早做。治理规则、权限边界、审计和门禁配置好之后，才可以相对放心地放开执行。

治理不是为了让 Agent 每一步都被拦住，而是为了让它在明确边界内少走弯路。只要限制合并、部署和高风险操作的规则足够清楚，再配合定期扫描和修复，就不必把所有注意力都花在实时盯守上。

因此比较合理的顺序是：先治理，再配置环境，最后把明确的目标交给 Agent。治理解决“能不能安全做”，环境解决“能不能顺利做”，目标则解决“要做成什么”。

## 任务完成取决于四个因素

一个任务最终能否完成，我现在倾向于从四个方面理解：模型本身的能力、初始上下文、动态环境，以及问题本身的难度。

初始上下文包括 prompt、skill 和任务说明；动态环境包括 Agent 能调用的工具、能检索的记忆、能看到的反馈，以及部署服务提供的执行条件。问题本身也有不同维度的难度：有的问题搜索空间很大，需要模型探索正确路径；有的问题只是步骤太多，需要被拆成多个阶段。

这意味着，提升 Agent 的效果不只是换更强的模型。还可以优化初始 prompt，清理和改善动态环境，把复杂问题拆解成更小的节点，并为常见流程提供必要的先验。

## Workflow 是降低难度的工具

复杂任务不适合一次性交给一个 Agent 从头做到尾。Workflow 的作用，是把大问题拆成多个阶段，让每个节点只处理更明确的一部分上下文和决策。

拆解不仅减少上下文长度，也会降低问题本身的难度。一个高级 Agent 可以先完成任务分解，再让不同节点分别执行、审计和验证。部分环节可以压缩成脚本，部分环节交给模型判断；节点之间通过门禁传递结果，减少幻觉和信息丢失。

因此，Workflow 并不是额外的形式主义，而是把原本很大的搜索空间切开，让模型在更小、更清晰的问题上发挥能力。

## 从盯守转向目标驱动

部署服务上线后，我感到最明显的变化是：不必无休止地和 Agent 交互，也不必假装忙碌地守在电脑前。更重要的工作，是明确目标、做好治理、配置环境，再让 Agent 放开去执行。

未来我希望把更多精力放在聊天开发和需求细节上，而不是反复指导每一个中间步骤。只要治理能够把系统拉回正确轨道，环境能够提供连续反馈，Agent 就应该被允许沿着目标持续推进。

最终的方向很简单：少一点人工盯守，多一点环境设计；少一点临时救火，多一点治理和 Workflow；让 Agent 不只是完成一次任务，而是在一个可靠的环境里持续把目标做完。
