最近越来越强烈地感觉到，人生的时间并不多。真正重要的事情，是用时间创作出一些东西，而不是把自己消耗在反复盯守、不断确认和看似忙碌的交互里。

## 从盯着 Agent，到配置一个能自己完成任务的环境

过去遇到自动化任务时，我常常担心它在某一步出错，于是给每个阶段加限制，自己守在电脑前不断输入管理员密码、确认下一步。结果任务没有真正持续执行，人的时间反而被切成了许多等待和干预的片段。

更合理的方式，是把部署、权限和工具配置成一个明确的环境，让一个服务只负责严格的部署动作，其他任务交给不同的 Agent 去完成。先设定目标，再设计一条能够持续运行的过程，让系统在我不在电脑前时也能继续工作，直到完成。

这不是放弃控制，而是把控制从“每一步都亲自盯着”转移到“提前设计好目标、边界和环境”。前者不断消耗人的注意力，后者则把时间投入到更高价值的规划和创作中。

## 复杂任务为什么需要工作流

和同事讨论 Agent 的自我进化时，我重新思考了工作流的意义。一个大的现实任务，往往不能直接交给模型从头做到尾。它需要被拆解成一组更小的节点任务，每个节点都有清晰的输入、输出和状态转移。

一个节点任务的完成，取决于几个部分：模型本身的智能、提示词、当前上下文，以及模型能够检索到的记忆、资料和工具。记忆和资料库并不是抽象的背景，它们构成了 Agent 的索引材料；工具和权限则构成它实际可用的环境。

当一个大任务被拆成足够小的节点，每个节点就可以在有限上下文中完成一件相对明确的事情。节点之间再通过工作流衔接起来，并用门禁检查各阶段的通信和输出，从而降低幻觉和信息丢失的风险。

## 能力提升不只是换更强的模型

Agent 能力的提升，当然包括模型智能本身的提升，但不止于此。还需要同时优化提示词、可检索的材料、工具环境、流程模式和任务粒度。

我倾向于把上下文区分成两类：静态上下文是这一次节点任务直接需要的内容，动态上下文则是这个节点背后所处的完整工作背景。只有把两者结合起来，节点才不会只看见眼前的一小段指令，却不知道自己在整个工作流中承担什么作用。

这也解释了为什么任务分解如此重要。不是所有环节都需要模型从头推理到底；有些环节可以被脚本压缩处理，有些环节需要模型运用判断力。把适合脚本的部分固定下来，把需要智能的部分交给模型，再为每个节点提供足够而不过量的上下文，系统才更有可能稳定运行。

## 把时间用在目标型工作上

目标型执行的核心，不是让 Agent 看起来一直很忙，而是让它在明确目标下持续向完成状态前进。人的工作也一样：与其不断处理即时的小问题，不如把时间投入到目标、环境和流程的设计上。

只要任务被拆解得足够细，输入和输出足够清晰，配合合适的门禁和环境，许多原本难以一次完成的工作，就可以被压缩成一组可以持续推进的节点。

人生有限，应该少一点盯守，多一点创作；少一点假装忙碌的交互，多一点目标、环境与流程的建设。最终要解决的问题是：怎样让系统在我不在电脑前时，也能持续干活，干到完成。
